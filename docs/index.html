Claude Code plugin/ v0.2.0/ MIT/ independent port of Atomic

A verification harness that lives inside Claude Code.

atomic-cc is a plugin, and only a plugin. There is no separate CLI to learn, no daemon to keep alive, no service to sign up for and no API key of its own. You install it into the Claude Code session you already use, and nine workflows, ten subagents, five slash commands and four hooks appear at the prompt.

§ 01Nothing
to run

It is a plugin, not a program you run alongside Claude Code.

Most tools that promise verified agent output ask you to adopt a second thing: their binary, their orchestrator, their dashboard, their key. atomic-cc asks for none of that. Its workflows execute in Claude Code's own dynamic-workflow runtime, its agents are Claude Code subagents, its commands are Claude Code skills, and its enforcement is three POSIX shell scripts that Claude Code invokes as hooks.

The practical consequence: the gate travels with the plugin. Install it at project scope and the choice is recorded in the repository's own settings rather than your personal ones — there is nothing to remember to start, and nothing to leave running.

What gets installed

  • Four workflow scripts, run by Claude Code's workflow runtime
  • Ten subagent definitions, each with its own tool allowlist
  • Four skills, exposed as /atomic:* slash commands
  • Three shell hooks wired to PostToolUse, PreToolUse and Stop
  • A per-project .atomic-cc/ directory of run state and evidence

What does not

  • No CLI binary and no second command to learn
  • No daemon, watcher or background process
  • No hosted service, account or dashboard
  • No API keys, tokens or credentials of its own
  • No Node, Python or package installation step
§ 02Four
workflows

Four ways to make an agent prove its work.

Each workflow is invoked as a slash command and takes a single JSON object. A run_id is required and must match [A-Za-z0-9._-], at most 64 characters — it becomes a directory name, and the scripts deliberately cannot generate one for you, because a random id would break resume.

/atomic:goalquorum 2 of 3

A bounded implementation loop. Each turn a worker implements against acceptance criteria that are restated verbatim and never reinterpreted, then three independent reviewers inspect the real checkout delta in fresh context. Two approvals finish the run. The same blocking finding surviving three consecutive turns marks the run blocked instead of looping forever. Terminal states are complete, blocked or needs_human; a pull request is optional.

/atomic:ralphunanimous

The full pipeline for a rough prompt: refine it into a spec with testable acceptance criteria, run three researchers in parallel over the codebase and the documentation, implement, then hold a review gate that needs every reviewer to approve. Failed gates produce a bounded repair loop that is handed only the blocking findings, so the scope cannot drift.

/atomic:adversarial-verificationunanimity override

The sharpest of the four. A worker writes a candidate record of what it did and what it observed; N fresh-context verifiers return a bare pass/fail with evidence, deriving their checks from a rubric before they are allowed to trust the candidate; a separate fresh-context reducer decides accept, repair or reject. Its "accept" only stands if every verifier passed — that last check is arithmetic, not judgement.

/atomic:fan-out-synthesizeno gate

Research, not enforcement. Partition a task into independent branches, run them in batches bounded by max_concurrency, then hold a synthesis barrier that reads every branch artifact together, resolves contradictions explicitly and flags anything a branch claimed without evidence.

Ten subagents

Nine are ported from Atomic; the tenth, verifier, exists because Claude Code needs a named agent type where Atomic runs verification as a fresh-context workflow stage.

AgentRole
workerThe only agent that writes code in a run. Escalates product, architecture and scope decisions instead of taking them.
verifierDerives probes from the literal criteria before reading any receipt, inspects the checkout itself, and reports only evidence-backed findings.
debuggerReproduce, prove the root cause with file:line evidence, fix minimally, rerun the exact failing scenario.
code-simplifierBehaviour-preserving cleanup of the diff only; a simplification that breaks a test is reverted, not patched around.
codebase-locatorFinds where things live. Read-only reconnaissance, no analysis.
codebase-analyzerExplains how the located code actually works, tracing data flow with file:line references.
codebase-pattern-finderFinds existing precedents to model new work on, and says which one wins when conventions conflict.
codebase-online-researcherPrimary-source research with a URL behind every claim; unsourced claims are dropped or marked unverified.
codebase-research-locatorFinds prior internal specs, ADRs and research documents relevant to the task.
codebase-research-analyzerTurns those documents into constraints, marking each one applicable, stale or superseded.

Only worker, debugger and code-simplifier can edit files. The six research agents never touch source; codebase-online-researcher may write research notes under .atomic-cc/, and that is all.

§ 03Deterministic
convergence

The decision to approve is arithmetic, and it happens outside the model.

Asking a model whether its own work is good enough is not verification. atomic-cc's convergence rules are ported faithfully from Atomic's reducers, and they are built on one idea: reviewers emit a single boolean, and code — not a model — decides what that boolean means.

One authoritative signal

A reviewer's stop_review_loop boolean is the only thing that can approve a run. Its output is schema-validated, so a reviewer cannot approve by writing prose that sounds approving.

Approval is never recomputed

The reducer counts approving reviewers against a quorum and stops there. It never re-derives approval from the findings or the traceability table — upstream deleted that recompute because it deadlocked runs whose own criteria mentioned the review process.

Findings drive repair, not the gate

The blocking classification (required_by_objective always blocks; consistent_with_objective blocks at priority 0–2; out-of-scope and contradicting findings never block) builds the repair payload handed to the next worker turn. It has no vote.

Failure never approves

A reviewer that reports a reviewer_error does not approve — and does not abort the run either. Fewer reviewers returning than were requested is not convergence: it is another loop.

A model can reason badly. What it cannot do is turn bad reasoning into an unverified commit.

WorkflowApproval ruleBound

Four hooks hold the line

Evidence loggerPostToolUse · Bash

Every build, test and typecheck command run by any agent is appended to .atomic-cc/evidence/<session>.jsonl with its real stdout and stderr, and the agent that ran it. Verifiers cross-check claims against that log: a "tests pass" with no matching entry is a finding, not a proof.

Approval gatePreToolUse · Bash

While a run is active and unapproved, git commit and git push are denied — including the wrapped forms agents reach for, such as cd pkg && git commit or git -C dir push. With no active run it never interferes.

Stop guardStop

A turn cannot end quietly while run-state.json still says in_progress: the run has to be driven to a terminal state first. Bounded to three blocks per run, so it can never trap a session.

Upstream watchSessionStart · startup

At most once a day, compares the HEAD of bastani-inc/atomic against the commit recorded in upstream.lock. On drift it asks the session to suggest /atomic:sync-upstream, which reviews the upstream changes and updates the port. Fails open: no network, no git, no lock file — no noise.

Honest caveatThe enforcement hooks need jq on PATH and fail open without it — no jq, no gate. It is a declared trade-off, not an accident, and it is why jq is listed as a prerequisite.

§ 04Install

Three commands, and it is in your session.

The repository is its own single-plugin marketplace, so a clone is all Claude Code needs.

install
# 1 · clone the repository
git clone https://github.com/uppifyagency/atomic-cc

# 2 · register the clone as a marketplace
claude plugin marketplace add ./atomic-cc

# 3 · install the plugin from it
claude plugin install atomic@atomic-cc

Add --scope project to either command to record the choice in the repository's own settings instead of your personal ones. To try the plugin without registering anything at all, point a single session at the directory:

try it once
claude --plugin-dir ./atomic-cc

Requirements

  • Claude Code 2.1.154 or newer — earlier versions have no dynamic workflows.
  • A paid plan. On Pro, enable workflows in /config.
  • jq on PATH, or the hooks silently disable themselves.
  • Budget for real agents. An adversarial-verification run at standard rigor costs roughly 4–12 agent invocations.

Four slash commands for the human

CommandWhat it does
/atomic:statusReads the run state: receipts, ledger, blockers, approval, and a summary of the evidence log.
/atomic:approveThe human override. Seals approval and opens the commit gate — and states plainly when it is overriding an unconverged verification.
/atomic:resumeCross-session re-entry, reconstructed from the persisted receipts, ledger and last decision.
/atomic:rigorSets the effort profile: lean (1 verifier, 1 repair), standard (3, 2) or thorough (5, 4).

All four are marked disable-model-invocation: Claude cannot call them on its own. Approving a run stays a human act.

§ 05A run,
end to end

What a gated run actually looks like.

session · illustrative
/atomic:adversarial-verification {"run_id": "av-login-fix-01",
  "task": "Fix the login redirect loop",
  "criteria": ["/login redirects authenticated users to /dashboard",
               "existing auth tests still pass"]}

  Implement  · worker writes the fix and a candidate record
  Verify     · 3 fresh verifiers rerun the tests themselves
  Reduce     · 2 of 3 passed → not unanimous → repair
  Repair     · worker fixes only the blocking findings
  Verify     · 3 of 3 passed
  Reduce     · accept · approval.json sealed

Had the reducer not accepted, a commit attempt would have been refused by the hook rather than by a polite refusal in the transcript:

PreToolUse · deny
agent attempted → git commit -m "fix login redirect"

atomic-cc: run "av-login-fix-01" is not approved yet - the
deterministic reducer (or /atomic:approve) must seal
approval.json first. Check /atomic:status.

Everything a run knows about itself is on disk, in the project, in plain text — which is what makes /atomic:status and /atomic:resume possible after the session that started the run is long gone.

.atomic-cc/
.atomic-cc/
├── run-state.json            # active run + status
├── evidence/<session>.jsonl  # real command logs, from the hook
└── runs/<run_id>/
    ├── receipt-*.json        # worker receipts
    ├── ledger.jsonl          # goal-workflow ledger
    ├── decision.json         # last reducer decision, if unconverged
    └── approval.json         # written ONLY on approval

Add .atomic-cc/ to your .gitignore unless you want the run history committed.

§ 06Honest
limits

What it cannot do, and where it is still young.

A verification tool that oversells itself is worse than none, so: atomic-cc is version 0.2.0. The convergence rules are ported carefully and the hooks do what this page says they do, but the project is new and has not been through many hands.

It cannot fix reasoning

Nothing here stops a model from thinking badly. It stops bad thinking from becoming an unverified commit. Those are different promises, and only the second one is made.

Two things to confirm on your first run

Whether agentType wants the namespaced name (atomic:verifier) or the bare one — the runtime error lists what it accepts — and whether your plan exposes dynamic workflows at all.

Deliberate gaps against upstream Atomic

No context:"fork" stages. Native workflow resume with cached results is same-session only, so cross-session re-entry goes through /atomic:resume and the persisted artifacts. No mid-run human prompts — use /atomic:approve and split the work into phases. Atomic's file-based ctx.task plumbing is emulated by having agents read and write project files under .atomic-cc/.

The gate is not a sandbox

It denies git commit and git push from the Bash tool while a run is unapproved. It is a discipline for agents, not a security boundary against a determined one, and it fails open without jq.

Verification is not free

Every reviewer is a real agent doing real work. Thorough rigor means five of them per round. Use /atomic:rigor lean for small changes and save the expensive profile for the money paths.
